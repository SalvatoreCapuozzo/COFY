This pipeline isn't fully reproducible at fixed seed — why, and how much

Root cause: fedyolo only ever called torch.manual_seed() — Python's own random module and NumPy's RNG were never seeded anywhere in the codebase, even though ultralytics' own augmentation pipeline (mosaic composition, random-perspective jitter, HSV color jitter, crop offsets — confirmed directly in ultralytics/data/augment.py) draws from exactly those two, not from torch's RNG. So every batch's actual augmentation was effectively unseeded regardless of cfg.seed. Fixed in client.py, server.py, centralized.py (covers oracle.py too), and simulate_to_target.py. MPS backend non-determinism may still contribute at the margin (Apple's MPS doesn't fully support PyTorch's deterministic-algorithms mode), but the missing seed calls were the larger, fixable gap.

A second, structural source specific to async: client.py reseeds every RNG with cfg.seed + round_idx per node round. Under sync, round_idx is fixed (nodes always train in the same list order), so this is fully deterministic. Under async, round_idx is the live cross-node submission counter — which node's thread finishes and pushes first is a genuine wall-clock race no seed controls. Even with every RNG now seeded, async can still draw a different sequence of per-round seeds across runs.

How much this actually matters, from 4 same-config federated reruns post-fix: two sync configs landed within 0.001 and 0.024 mAP50 of their older siblings; two async configs split — one within 0.031 (nearly as tight as sync), one off by 0.13. The mechanism above explains why async can drift more than sync; it doesn't yet explain why one async config drifted 4x more than the other under the identical mechanism — an open question, not resolved.

Centralized/oracle training is a different story — and a clean one. Unlike federated training, neither has any thread-race or node-ordering step at all (both are single-threaded, sequential loops), so the round_idx mechanism above doesn't apply to them. Direct confirmation: yolo26-classic@l640's sync-invocation and async-invocation each independently trained their own centralized and oracle baselines, and both came back bit-for-bit identical — 0.6142542185317407 both times, down to per-class AP50. Post-fix, centralized/oracle training is fully reproducible on this pipeline; the non-determinism documented above is specifically a federated-training (and mainly an async-federated-training) phenomenon, not a general property of this codebase. Full writeup in the field report §5e/§5g.

Note: what "Cent" and "Oracle" each actually measure

This table carries two different baselines for a reason — they answer two different questions, and conflating them is the easiest way to misread every ratio in this report.

Cent — the partial-label baseline

One model, one optimizer, cycling through all four nodes' dataloaders in sequence every epoch, re-masking the loss to each node's owned classes as it switches. It sees the same partial-label constraint federated training faces — no node's images are ever labeled for a class it doesn't own — just without aggregation across separate copies. It answers: does aggregating independently-trained per-node copies beat directly cycling one shared set of weights through the same nodes?

Oracle — the full-annotation ceiling

fedyolo/oracle.py + --also-oracle builds a true fifth node with every one of the 12 classes labeled on every one of its 15,448 images — no masking anywhere. It answers a harder question: how much detection quality does the partial-label constraint itself cost, regardless of how training is organized? This is the number "Cent" can never reveal, because Cent shares that same constraint.

Federated beating centralized outright is a real result here, not noise to explain away. Rows 3 and 4 (yolo26-classic@x640, yolov8m@640) beat their own centralized baseline in both sync and async legs, and most rows beat it in at least one. The mechanism is concrete: Cent's single optimizer carries momentum from node A's class-masked gradient directly into node B's differently-masked batch on the very next step — a real source of interference when one optimizer chases a target that changes every few batches. Federated sidesteps this entirely by giving each node its own fresh local optimizer and only reconciling at the (cheaper) aggregation step. Aggregating independently-trained copies is, on this evidence, a genuinely competitive strategy against training one model through the same partial-label constraint sequentially — not merely "not worse."

17 of this table's 19 rows now carry an oracle ratio (only rows 12 and 13 — yolov8s@s480 and yolo26-classic@s480 — still don't, predating the oracle baseline's existence). Row 2 (yolo26-e2e@x640, sync) holds the highest oracle ratio in the whole table — 87%. The low end sits inside yoloe specifically: row 19 (yoloe@s480, sync) at 38% and row 10 (yoloe@m640, sync) at 46% are the two lowest oracle ratios of any config here, both sync-mode yoloe legs — consistent with yoloe having the widest sync/async gap of any architecture on this table. Outside yoloe, no clean sync-vs-async split and no clean scale trend — architecture looks like it matters more than sync-vs-async once yoloe's own separate weakness is set aside. See the non-determinism callout below for the residual noise this doesn't rule out, and the reliability section further down for how consistent the Fed:Cent ratio itself is across everything tested so far.

Meanwhile cv2's 0.783 cosine is a clean confirmation of the macro-object hypothesis this project has argued from the start: box geometry genuinely transfers across nodes that share no classes.

Does federation stay within 10% of centralized? A pre-registered, three-dataset test

The question this whole project has to answer, now framed so it can be answered: across three clinical datasets, do synchronous and asynchronous federated training each keep at least 90% of centralized detection performance? The test was written down before any run under it existed, and before any result on the third dataset existed — fedyolo_system/analysis/PREREGISTRATION.md, fixed 2026-09-23 — and is computed by tools/analyze_study.py, also written before any result.

The test

Per training seed, r = federated mAP50 ÷ centralized mAP50, both on the dataset's held-out, fully-labeled eval set. Over 5 seeds, the lower bound of the two-sided 95% confidence interval of the mean must reach 90%. That is a one-sided non-inferiority test at α = 0.025. It must pass for sync and async on every dataset — six tests, all required.

Held fixed: yolo26-classic@l640, plain FedAvg (no merge improvements), the same hyperparameters as every earlier l640 run. Fed:Oracle is reported alongside, without a pass/fail threshold.

ChestX-Det10 trains on 50% of its images rather than 10%, so all three datasets train on a comparable 1,068–1,507 unique images; at 10% it would have ~220, too few to learn ten X-ray findings. Its split passes the same six invariants, and conversion lost no image and no box. Its 764 images with no finding are excluded, as neither other dataset has object-free images.

A second evaluation flaw, found and fixed before the study

The node splitter drew a separate train/val split for every node. That is harmless when each image belongs to one node (WBC), but not when an image holds several classes owned by different nodes (kfm12, and ChestX even more so): the same image could land in one node's train split and another's val split, and the pooled eval set then held several copies of it, each with a different partial set of labels. A correct detection of the other node's class on the "wrong" copy scored as a false positive. On kfm12, 608 eval images (17.9%) had been trained on by some node, and 162 eval entries were such duplicates.

The splitter now draws one image-level split for the whole dataset (--split-mode global, the new default). Train images go to nodes with partial labels, as before; val images form a single, fully-labeled, deduplicated eval set that federated, centralized and oracle are all scored on; the oracle trains on the same train pool with full labels. Six invariants were checked on kfm12 — no image straddles train and val, the eval set shares nothing with any training pool, has no duplicates, loses no box, and the node and oracle training pools are identical — and all six pass. Node ownership is unchanged on both existing datasets.

Before re-running, the existing kfm12 checkpoints were re-scored on 543 images that no model had ever trained on, with full labels. Two things came out of it.

How sync and async actually run, on top of a YOLO model

Both modes share the exact same per-node model and the exact same parameter split (below) — they only differ in when a node's update reaches the server and how the server merges it in. This split is what makes federating across nodes that own different, non-overlapping classes possible at all.

YOLOv8 / YOLO26 classic-head (Phase 1) — the split sync and async both aggregate the same way

Node D owning only ascaris and ancylostoma still contributes its backbone/neck gradients to every other node's shared weights every round — it just never touches node A's calicophoron row of the final conv, and vice versa. This is exactly the mechanism behind the "macro-object" hypothesis tested in §6 of the full report: shared low/mid-level features transfer even when label sets don't overlap at all.

YOLO26 native end-to-end (Phase 2) — the same split, doubled

YOLOE — nothing per-class to split at all

Sync — round-barrier FedAvg (FedServer, ProcessPoolExecutor)

One node in the pool per node per round, run via mp.get_context("spawn") subprocesses (the "extra python process" investigated earlier in this report is exactly one of these). A round is only as fast as its slowest node — with max_concurrent_nodes: 1 on this machine, "parallel" above is actually serialized to fit in 16GB, so a sync round's wall-clock is roughly 4× one node's local_epochs.

Async — staleness-discounted delta updates (AsyncFedServer, ThreadPoolExecutor)

Nodes never wait on each other — a slow node (bigger arch, bigger image size) just contributes a more-stale, more-discounted update instead of blocking the other three. This is the structural reason async keeps beating sync on the federated/centralized ratio across every config in the leaderboard above: sync's barrier means the whole federation moves at the slowest node's pace every single round, while async's staleness discount absorbs that instead of forcing everyone to wait.

The merge itself: which parameter gets which rule, upload to broadcast

The diagrams above show when an update reaches the server; this is what happens to every parameter tensor once it does — the actual decision the server makes for each key in a node's uploaded state_dict, stated precisely enough to reimplement, not just described in prose.

Formal update rules — sync (round-barrier FedAvg) vs. async (staleness-weighted delta)

Both share the same routing above; they differ in how the averages are computed and when. Notation: K nodes, node k owns global class ids owned(k); Θ_S = shared parameters, Θ_C[c] = per-class row for class c; n_k = node k's image count, m_{k,c} = node k's labeled-instance count for class c (floored at 1 to avoid a div-by-zero for an owning node with momentarily zero instances in a subsampled batch).

Algorithm 1 — Sync round r → r+1 (fedyolo.server.FedServer.run)
1  broadcast (Θ_S^r, {Θ_C[c]^r : c ∈ owned(k)}) to every node k = 1..K
2  for k = 1..K in parallel (up to max_concurrent_nodes at once):
3      θ_k ← LocalTrain(Θ^r, D_k, local_epochs)   # loss masked to owned(k) only
4  barrier: wait until all K nodes have returned θ_k
5  Θ_S^{r+1} ← Σ_k (n_k / Σ_j n_j) · θ_k,S                    # every node contributes
6  for each global class c:
7      owners(c) ← { k : c ∈ owned(k) }
8      if owners(c) = ∅: Θ_C[c]^{r+1} ← Θ_C[c]^r        # unchanged, defensive only
9      else: Θ_C[c]^{r+1} ← Σ_{k∈owners(c)} (m_{k,c} / Σ_{j∈owners(c)} m_{j,c}) · θ_k,C[c]
10 r ← r + 1; goto line 1
Algorithm 2 — Async, one node's event loop (fedyolo.server.AsyncFedServer._node_loop / push)
1  for cycle = 1..async_node_cycles independently per node (no cross-node sync at all):
2      (Θ_v, v) ← Pull()                          # current global weights + version counter
3      θ_k ← LocalTrain(Θ_v, D_k, local_epochs)   # same masked loss as sync
4      Push(θ_k, Θ_v, v)                          # server-side, under a lock:
5          τ ← v_current − v                      # staleness: how many pushes landed since this node's pull
6          w ← 1 / (1 + α · τ)                    # α = federation.staleness_alpha
7          Θ_S ← Θ_S + w · (θ_k,S − Θ_v,S)         # DELTA, not a fresh average — this node's own local update
8          for c ∈ owned(k):                    # only rows this node actually owns move at all
9              Θ_C[c] ← Θ_C[c] + w · (θ_k,C[c] − Θ_v,C[c])
10         v_current ← v_current + 1              # immediately -- no wait for any other node

The async rule is genuinely not "FedAvg run once per push" — it applies node k's own local delta (its trained weights minus the exact snapshot it started from) directly to whatever the global model has become by the time the push lands, discounted by how much that global model has already moved on without it. Two real consequences worth being explicit about: (1) a node's contribution is genuinely lost information if τ is large enough that w rounds to negligible — a real, tunable trade-off in α, not a bug; (2) unlike sync's per-class average (line 9 of Algorithm 1, a weighted mean across every current owner), async's per-class update (line 9 of Algorithm 2) never looks at other owners' state at push time at all — each owning node's delta lands independently, so the "average across owners" property only holds in aggregate, over many pushes, not at any single instant.

fedyolo.net: real client-server federation

Everything above runs inside one Python process. fedyolo/net/ is a separate, additive subsystem that runs the same config-driven federation as an actual distributed system: a server process with a browser dashboard, and separate client processes — each its own GUI ("personal room") — that pull the global model, train locally on their own machine's own dataset, and push results back over real HTTP. federation.mode still decides sync vs. async. Works with everything on one Mac (one client process per simulated node) or spread across two Macs on the same Wi-Fi, with zero code differences either way.

Two room types. Static rooms load an existing config YAML exactly like every run above — nodes/classes fixed and server-authoritative. Dynamic rooms are built from scratch with just a class ceiling (max_classes): each client declares its own class names on join, and the server assigns global ids in order of first appearance, reusing an id if another node already claimed that name — genuinely realistic, since a real server doesn't know in advance what data a joining client actually has. Sync dynamic rooms freeze the node/class set once the operator hits Start (sync's barrier needs a fixed participant set); async ones stay open indefinitely, including to new classes an already-joined node declares mid-run.

Checkpoint history + rollback, room passwords, a client-side dataset builder (with a local file browser and an illustrated folder-layout guide) round out the rest. Full usage instructions in fedyolo/net/README.md; full build history in the field report.

What async rooms specifically make possible, verified against the actual room code

Async's delta-based, no-barrier update rule (Algorithm 2 above) isn't just a training-speed optimization — over a real network, with real clients joining and leaving on their own schedules, it changes what's actually operationally possible. Each claim below was checked directly against fedyolo/net/rooms.py, not assumed from the design intent.

A node can join after training has already started

Dynamic async rooms never auto-finish and never freeze their participant list — Room.join() has no "already started" check on the async path at all (only sync dynamic rooms block joining once the operator hits Start, because sync's barrier genuinely needs a fixed node count to know when a round is complete). A brand-new node can declare its own classes and start pulling/training/pushing at any point in an async room's life, including classes no earlier node ever owned — they start from random init and learn only from the cycles they're actually trained in from that point forward, same as any newly-added class.

No node ever waits on any other node

Pull → train → push is a closed loop per node (Algorithm 2, line 1: "independently per node — no cross-node sync at all"). There is no round counter shared across nodes, no barrier, and no server-side check of how many other nodes have submitted before accepting a push. A node can be offline for an hour and rejoin later with no special handling needed for the gap — its next pull simply returns whatever the global model has become, and its next push is discounted by whatever staleness that gap produced. Reconnection isn't a feature that had to be built; it falls out of the update rule having no notion of "on time" or "late" beyond the staleness weight itself.

A fast node can submit several updates before a slow node submits its first — verified, and the honest picture of what that does and doesn't do. Nothing in _node_loop() enforces turn-taking: each node's thread just runs its own for cycle in range(async_node_cycles) loop, gated only by a shared semaphore that limits how many nodes train concurrently (max_concurrent_nodes) — not whose turn it is or how many cycles anyone else has completed. A small model on a fast machine can genuinely finish 5 pull-train-push cycles in the time a large model on a slow machine finishes 1. This doesn't block, error, or penalize the slow node in any way — its eventual push still gets aggregated correctly, at whatever staleness it accumulated. What it does mean, stated plainly rather than glossed over: during that stretch, the shared parameters (backbone/neck/box-regression) receive proportionally more of their update signal from the fast node's own data distribution, simply because more of its deltas landed in that window — an inherent, expected property of staleness-weighted async aggregation (the same trade-off any published async-FL scheme with this update rule makes), not a defect specific to this implementation. It's a real reason to watch node training-speed balance when running a room with very mismatched hardware, not a reason to expect it to silently even itself out.

What sync rooms specifically make possible, verified the same way

Sync trades away async's elasticity for something else genuinely useful: a round-barrier means every aggregation event has a single, well-defined "everyone's in" moment — which unlocks a different set of real capabilities, not just a more restrictive version of async. Checked the same way, directly against the room code.

Every node's contribution is weighted only by its data, never by timing

Sync's shared-parameter update (Algorithm 1, line 5) is a pure image-count-weighted average across whichever nodes reported this round — Θ_S ← Σ_k (n_k/N)·θ_k,S, with no staleness term anywhere in it. A node's influence on the merged model depends only on how much data it owns, never on how fast its hardware is or when in the round its push happened to land — the opposite of async's honest fast-node-dominates-the-stretch caveat above. For a deployment that needs to reason about or audit exactly how much weight each participant had in a given round (a regulatory or multi-institution setting, for instance), sync's guarantee is simple enough to state in one sentence; async's genuinely isn't.

A closed, curated cohort — participation locks before training starts

Room.join() raises PermissionError for a dynamic sync room the instant the operator hits Start — registration is open only up to that point, then closes deliberately, by design (sync's barrier needs a fixed participant set to know when a round is complete at all). That's a real, distinct operating mode from async's always-open door: an operator can assemble an exact, known cohort — say, a fixed consortium of named institutions — confirm the full roster, and only then start training with certainty about exactly who is contributing. Static sync rooms get this for free too, since their node list is fixed by the config from the start.

The same round-barrier also makes sync's timing predictable in a way async structurally can't be: a round completes on a known cadence (bounded by the slowest current node's local_epochs), so the next aggregation — and the next checkpoint, and the next scheduled eval — happens at a knowable point, not whenever enough independent pushes happen to accumulate. That predictability is also why sync's Fed:Cent numbers reproduce far more tightly at fixed seed than async's (the non-determinism callout in the leaderboard section, and Algorithm 1's fixed node order vs. Algorithm 2's genuine wall-clock race) — the same barrier that costs sync its elasticity is what buys it that determinism.

Neither mode is strictly better than the other here — they trade the same underlying property (a hard barrier) for opposite things: async gets elasticity and no idle waiting at the cost of timing-dependent influence and looser reproducibility; sync gets a simple, auditable weighting rule and a closed, known cohort at the cost of moving at its slowest current member's pace and closing the door once training starts.

Now that every one of the 9 flagship configs has a sync leg — yolov8m@m480's first sync result just landed, at 96.5% — the sync mean has settled to a flat 100.0% with async's own 99.5%, essentially indistinguishable at this sample size; the extra seeds added for yolov8l@l640 and yolo26-e2e@l640 (110.1%/93.7% and 80.3%/89.1% sync respectively, alongside their original single-seed points) moved sync's own spread from 9.4 to 8.5 — still real seed-to-seed variance a single point per config couldn't show, just not larger this round. This is a genuine, reproducible property of the round-barrier update rule, not an artifact of any one run.

Read together with the oracle columns: the federation mechanism itself (the ratio charted here) and the partial-label annotation constraint (the roughly-constant ~75-85% Fed:Oracle band documented in the leaderboard section) are two separate, independently-behaving costs. Federating well doesn't close the annotation gap, and a wide annotation gap doesn't mean the federation mechanism itself is unreliable — the two numbers answer genuinely different questions.

Scope, stated plainly rather than as a deficiency: the chart above reflects one dataset (12-class parasite microscopy, 4 disjoint-class nodes), three architectures sharing the same per-class-head design, and flagship (m/l/x) scale only. A second dataset (White Blood Cell detection, own section below) now has its first real result — one config, both modes, both beating centralized the same way kfm12's own flagship does — too small a sample yet to fold into this chart's own statistics, but a genuine first step past the single-dataset limit. The more datasets, architectures, and scales that land in the same bands, the more confidently this generalizes; each new one tested either reinforces or narrows the current picture.

SOTA comparison: UltraFlwr

UltraFlwr's run below is sync, structurally — it has no async mode at all. It runs on stock Flower ( fl.server.start_server + FedAvg), which is a round-barrier protocol by construction: the server samples a client set, waits for every sampled client's fit() to return, and only then aggregates and starts the next round — the same shape as this project's own sync mode. There's no staleness-weighted merge, no node-submission-order aggregation, no equivalent of this project's async node-cycling anywhere in UltraFlwr's code — not a setting left off, a mode that doesn't exist in the framework. So the yolo11l result below isn't "UltraFlwr's sync run" as opposed to some async counterpart; it's simply how UltraFlwr trains, full stop, and the fairest comparison point for it is this project's own sync-mode rows.

Every client in this run had homogeneous class access — every client sees every class, just different images. Not a setting chosen for this comparison: checked directly in UltraFlwr's own source, and it has no mechanism at all for disjoint per-node class ownership like this project's own design. Its data splitter takes only an image-count ratio per client and copies whichever images land in that slice with their labels untouched — no per-class filtering, no owned-classes concept, no loss-masking anywhere in its training code. Homogeneous splitting isn't UltraFlwr's default mode, it's the only mode it supports. This is a real, structural difference between the two systems, not a knob either one turns.

Run on the same real image pool (kfm_250423_clean12's oracle pool), with models scale-matched to this project's own l640 flagships rather than UltraFlwr's own nano-only demo default. 2 clients (hardware-constrained down from 4 — Flower's protocol needs every client live and training concurrently, unlike this project's own throttled sequential node training, and this Mac's single MPS GPU can't share efficiently across processes), 500 train / 125 val images per client (hardware-constrained down from the full pool).
