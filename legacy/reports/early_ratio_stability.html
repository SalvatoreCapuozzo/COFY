COFY · statistical stability check

Does federating cost a predictable amount, or does it depend on what you train?

Every Fed:Cent and Fed:Oracle ratio from every run so far (19 configs, up to 4 architectures, 4 scales, both modes) — checked for whether they cluster into a band you could actually bet on, or scatter too wide to promise anything.

The short answer

Async mode
Yes — a real, tight band
94.1% ± 8.3 Fed:Cent across every architecture tried, including the one that struggles under sync. Individual runs ranged 81–114%, never below 81%.
Sync mode
No — architecture-dependent
88.0% ± 21.0 Fed:Cent overall — but that spread is almost entirely one architecture (YOLOE) landing at 50–63% while everything else lands 78–113%.

So: a confident "you won't lose more than about 15-20 points under async" is defensible from what's been run. The same claim for sync mode isn't — it depends on whether the target architecture's detect head behaves like YOLOE's or like everything else's, and that isn't knowable in advance without running it. See "what this can't tell you yet" below before treating either number as universal — both are still measured on one dataset.

95% confidence interval for the async Fed:Cent mean (not the individual-run range shown on the chart): [89.9%, 98.2%] across all 19 configs, [93.7%, 101.6%] excluding YOLOE — both computed with a t-distribution at the relevant degrees of freedom, not eyeballed. YOLOE's own sync legs are tight among themselves (56.2% ± 4.7) — this isn't sync being noisy, it's sync being consistently worse specifically for YOLOE's open-vocabulary detect head, a real architectural interaction rather than random variance.

What this can't tell you yet

Zero dataset variation
All 19 configs, 1 dataset
Every single run — every architecture, every scale, both modes — trained on the exact same 12-class kfm_250423_clean12 split, same 4-node ownership, same balanced_fraction. This can only speak to "does the ratio hold across models on this dataset." It says nothing about a different class count, class balance, or node-split shape.
Reseeding in progress, 1/9 done
N=1 run for 18 of 19 configs still
A reseed matrix (2 extra seeds each, for the 9 main-table configs) is running via run_matrix.py — paused by hand after its first config. yolo26-classic@l640 now has real 3-seed data (see its whisker on the chart above): sync ratio spans 95.7–109% (mean 100.5%), async spans 85.0–100.5% (mean 93.8%) — a real, non-trivial spread, wider on sync. The other 18 configs still carry unmeasured seed-noise in their single point estimate.
Small architecture count
4 genuinely distinct designs
19 configs sounds like a lot, but they're 4 detect-head designs (YOLOv8, YOLO26-classic, YOLO26 end-to-end, YOLOE) at various scales — scale variants aren't independent samples for an "any model" claim the way a 5th genuinely different architecture would be.

What to run next, to actually earn a cross-dataset claim

  1. A second, genuinely different dataset. Not a resample of the same source images — a different class count and a different class-imbalance shape, run through at least the flagship architecture (yolo26-classic) and the outlier (YOLOE), both modes. This is the single highest-value next step: right now there is no evidence either way for dataset generalization, since it's the one variable that has never moved.
  2. 2-3 seeds on a handful of configs spanning the range already seen (a strong sync config, a weak one, an async one) — enough to separate real architecture-driven variance from the seed-noise already documented (the async non-determinism callout in the current-state report) without reseeding all 19.
  3. One more genuinely distinct architecture if one becomes available, ideally with a different aggregation-relevant property than the current four (e.g. an anchor-based or transformer-based detector) — the current four-architecture base is enough to trust the async band cautiously, not enough to call it settled.
