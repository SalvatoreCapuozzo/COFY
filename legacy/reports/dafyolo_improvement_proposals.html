Design proposal · nothing below is built yet

Merging YOLO models that share no classes at all

WBC's federated result trails its own full-annotation oracle by far more than kfm12's does (52–58% vs. 72–83% Fed:Oracle). Three constraints are fixed and not up for negotiation: nodes stay mutually independent, the server never holds a labeled image, and class ownership stays extreme non-IID — one class, one node. Inside those walls the real question is narrow and concrete: how do you merge four detectors that were each trained to find entirely different objects, without averaging away what each one learned? Everything below is additive — sync and async both stay exactly as they are.

The three walls, and what they rule out

1 · Nodes are mutually independent

A node learns that another class exists only by downloading the server's model. Verified: cofy/net/'s dynamic rooms already work this way (rooms.py:219-267 — a class ceiling, placeholder names, and join() returns a node only its own classes). Today's simulate.py static configs do not — one YAML carries the full class list to every node before round 1. Treated here as a rule for new work, not a retroactive fix to the reported pipeline.

2 · The server holds no labeled images

It receives weights and nothing else. No server-side evaluation set, no calibration slice, no fine-tuning pass of its own.

3 · Ownership stays extreme non-IID

One class, exactly one node, disjoint. Confirmed in both datasets — WBC's 1+1+2+3 = 7 and kfm12's 3+4+3+2 = 12. Not a parameter to tune; the condition being studied.

Three earlier draft items are gone rather than reworked, each failing one wall: exchanging object crops between nodes (wall 1), a small server-side full-class calibration set fine-tuned between rounds (wall 2), and replicating each class across two nodes to give the per-class averaging path something real to average (wall 3).

The merge problem, measured

Two facts about what merging currently does, both taken from a real WBC yolo26-classic@l640 checkpoint and the aggregation code itself.

First — the per-class split protects almost nothing. The architecture's centerpiece is separating per-class parameters from shared ones, so that a node never overwrites a class it knows nothing about. In practice that protected set is cv3.{i}.2's weight and bias: 5,397 parameters out of 24,845,185. Everything else — 99.98% of the model — is coordinate-averaged across four nodes that share no classes whatsoever.

Second — under single ownership, even that sliver is never actually averaged. aggregate_per_class (model.py:368-386) builds contributors = [i for i, owned in enumerate(...) if c in owned] and takes an instance-weighted mean over them. With exactly one contributor that weight is 1.0, so the output is that node's own row unchanged — an identity operation, in every experiment this project has run. The per-class machinery's real job has been isolation, never averaging. Which also means head-personalization methods (FedPer and relatives) have nothing to offer here: the head is already maximally personalized by construction.

Put together: the entire federation reduces to merging one shared trunk across four models that were optimized for disjoint objectives. That is the whole problem, and it is where every technique below is aimed. Of the shared parameters, the 557,068 in cv3.{i}.0 and cv3.{i}.1 were the prime suspect, sitting immediately before the per-class layer. Measured, they are not the problem: at the first aggregation they retain 0.721 of their update at a cross-node cosine of 0.651, while the backbone retains only 0.585 at a cosine of 0.103. The disagreement is in the trunk.

Track M — better merge rules

Server-side changes to how node weights combine. All of them see only weights, none needs a node to know anything new, and none touches class ownership.

M2
Merge the classification branch more slowly than the trunk
low costserver-side onlyfollows directly from the measurement above

Premise refuted by measurement. The merge diagnostic found these convs among the best-aligned parameters across nodes (retained 0.721, cosine 0.651), and the backbone the worst (0.585, 0.103). As written, this is aimed at the wrong layer; the damped-merge idea only survives if re-aimed at the trunk.

Backbone and neck learn generic low- and mid-level visual features that plausibly transfer between cell types — that is the "macro-object" hypothesis this project already argues for. cv3.{i}.0 and cv3.{i}.1 are different: they exist to make features that separate this node's classes from background, and nothing else. Averaging them at the same rate as the backbone treats the most contested parameters in the model as if they were the least.

Cheapest version: a per-layer-group merge rate — the trunk takes the full aggregate, the classification convs take a damped step toward it (keeping more of the previous global value). One coefficient, no architecture change, no new state beyond what the server already holds. Worth pairing with a diagnostic that costs nothing: log the cross-node cosine similarity of each layer group's deltas per round. If the classification convs really are where nodes disagree most, that shows up immediately and tells you how hard to damp.

Touches: cofy/model.py aggregate_shared() (layer-group aware) · one new coefficient
M3
Give each node its own classification-branch head
moderate costarchitecture changethe structural version of M2

If the classification convs are irreconcilable between nodes, the honest answer may be to stop reconciling them. Give each node its own copy of cv3.{i}.0/.1 plus its own final per-class rows — one head branch per owner — and merge only the trunk and the box branch. At inference the global model runs every branch and concatenates their class outputs.

This extends the project's own thesis rather than departing from it: the current design already says "parameters that are about a specific class must not be averaged across nodes that don't own it." The measurement above says the split was simply drawn one layer too shallow — cv3.{i}.2 alone is 0.02% of the model, while the convs feeding it are 2.24% and just as class-specific.

Cost is real but bounded: replicating the mixing convs four ways adds roughly 1.7M parameters to a 24.8M model, about +7%. Note the split cannot be done by row-indexing the way cv3.{i}.2 is — those convs output a fixed channel width, not one channel per class — so this is a genuine head-structure change, not a change to per_class_param_names().

Touches: cofy/model.py (head construction + aggregation), cofy/evaluate.py (multi-branch inference)
M4
Weight the trunk merge by supervision, not by image count
low costan inconsistency already in the code

Measured scope: a provable no-op on WBC, where every image carries exactly one object so instance and image counts coincide. On kfm12 it is large — node_B falls from 41.9% to 24.7% of the merge weight and node_D rises from 14.7% to 26.8% — so kfm12 is where it has to be tested.

The two aggregation paths disagree with each other today: aggregate_shared weights each node by its image count, while aggregate_per_class weights by labeled-instance count. Under extreme non-IID the two diverge in a way that matters — a node's images are only labeled for its own classes, so image count measures how much data a node holds, not how much supervision it actually contributed to the shared trunk. A node owning one class and a node owning three contribute very differently to the trunk even at equal image counts.

Cheap to test both ways: switch the trunk to instance-count weighting and see whether the reliability chart's spread moves. A one-line change with a clear prediction attached.

Touches: cofy/server.py (node_weights passed to aggregate_shared)
M6
Stop averaging BatchNorm statistics across disjoint distributions
low costreal friction, narrower fix than the published method

Measured on the same checkpoint: 320 of 972 state-dict entries are BatchNorm running_mean/running_var buffers (160 BN layers). They're floating-point and not per-class keys, so aggregate_shared (model.py:336-345) averages every one. These are input-distribution statistics, and this federation is non-IID by construction — node_A's images are the ones with neutrophils in them, node_D's have basophils, lymphocytes and monocytes. Their mean describes no node's actual input. (The integer num_batches_tracked buffers are already handled sensibly — largest node's value, not a mean.)

Stated honestly: textbook FedBN does not transfer here. It assumes a personalized model per client, this project ships one global model, and the server cannot recalibrate statistics itself because it has no images. The applicable version is narrower and diagnostic — freeze BN running stats after a warmup period, or swap in a normalization layer with no cross-batch statistics at all, and see whether the spread moves. Cheap, and it would explain something real if it does.

Touches: cofy/model.py (exclude BN buffers from aggregation) or the arch yaml
M7
Align channels before averaging (FedMA / Git Re-Basin family)
high costdiagnose first — may not be needed

Coordinate-wise averaging assumes node k's channel 17 means the same thing as node j's channel 17. Networks have permutation symmetry in their hidden units, so independently trained models can compute similar functions with differently ordered channels — averaging misaligned models damages both. The established fix is to match channels across clients (Hungarian matching, or optimal transport) before averaging.

Honest assessment: this matters most when clients train a long time between merges. Here every node reloads the identical global weights at the start of every round (client.py:111) and trains for two local epochs, which pins them close to a single basin and is much of why plain FedAvg works at all. So the payoff is uncertain — but it is measurable before committing: log cross-node channel correlation for a few layers just before aggregation. Near-perfect correlation means alignment is a non-problem and this can be dropped; visible drift means it's worth building. Run the diagnostic, not the technique.

Touches: a standalone diagnostic script first · full version touches cofy/model.py aggregation

Track D — give the merge less to reconcile

The complement to Track M: rather than merging divergence better, produce less of it. These constrain how far a node's weights can travel during local training, which is also the most likely explanation for sync's higher seed-to-seed spread (± 8.5, against async's ± 6.5).

D1
FedProx-style proximal term on local training
low costcheapest pilot in this doc

Add μ/2 · ‖θ_k − Θ^r‖² to each node's local loss (Algorithm 1 line 3 / Algorithm 2 line 3): a penalty pulling locally-trained weights back toward where the round started, bounding how far any node can drift before aggregation. Under disjoint classes each node's local optimum genuinely lies somewhere different, so unconstrained local training pulls hardest exactly where merging is hardest. One extra loss term, one new hyperparameter (federation.prox_mu), no architecture change.

Touches: cofy/client.py (local loss), cofy/config.py (one new field)
D2
SCAFFOLD-style control variates
high costmost principled, biggest lift

A per-node control variate that corrects local gradient direction toward an estimated global direction — the strongest published variance-reduction method for heterogeneity, and this heterogeneity is as severe as it gets: nodes differ not merely in data distribution but in which loss dimensions are active at all. Requires maintaining and transmitting an extra state vector per node, handled differently across sync's barrier and async's independent cycles. The thing to reach for if D1 leaves spread on the table — not the first build.

Touches: cofy/client.py, cofy/server.py, new per-node protocol state (incl. cofy/net/)
D3
Server-side momentum on the trunk update
moderate cost

Replace the plain weighted average Θ_S^{r+1} ← Σ_k (n_k/N)·θ_k,S with a momentum or Adam-style update on the round-over-round delta, leaving per-class rows on the current rule. Smooths round-to-round noise from whichever nodes happened to move furthest that round. Composes with the FedNova step normalization already in the code (normalize_steps) — that changes what the aggregate direction is, this changes how fast the global model follows it.

Touches: cofy/model.py aggregate_shared(), cofy/server.py (optimizer state)
D4
Rotate the sync node order across rounds
low costcheap diagnostic, uncertain payoff

Sync trains nodes in a fixed list order every round. If any one node's gradients disproportionately shape the early rounds before the model stabilizes, that's a systematic bias with a free fix. Purely structural — no new loss term, no new state — and worth running as a quick ablation before committing to D2 or D3.

Touches: cofy/server.py (FedServer round loop, ordering only)
D5
Adaptive staleness discount for async
low costlower priority — async is already tighter

Async uses a fixed staleness_alpha in w = 1/(1+α·τ) for the whole run. A schedule — decaying α as the global model stabilizes, or per-node α adapted to that node's historical disagreement with the aggregate — could tighten async further, but async's ± 6.5 is already the more reliable of the two modes, so this ranks below the sync-side work.

Touches: cofy/server.py (AsyncFedServer push handler)

Track S — when the merge happens: two new modes

Sync and async are two points in a space with more than two points in it. Both of these are new values for federation.mode, sitting between the existing pair rather than replacing either.

S1
Buffered async (FedBuff-style) — merge every K submissions, not every 1
moderate costa superset of both existing modes

Async applies each delta the moment it lands; sync waits for all N. A buffered mode accumulates deltas and applies their staleness-weighted mean once K have arrived. K=1 reproduces today's async exactly and K=N approximates sync, so the mode contains both and the interesting behavior is in between.

The reason to expect a win is precisely the Track M problem: averaging K deltas before applying them reduces the per-update noise that single-delta async injects, without reintroducing the hard barrier that makes sync move at its slowest member's pace. Fits the code shape — the async push handler already serializes under a lock, which is where the buffer would live.

Touches: cofy/server.py (AsyncFedServer push path), one new federation.buffer_k field
S2
Bounded-staleness semi-sync — a soft barrier instead of a hard one
low costcheapest of the new modes

Async lets a fast node run arbitrarily far ahead — the current-state report's own honest caveat is that during such a stretch the shared trunk absorbs disproportionately much of that node's data distribution, which under disjoint ownership means disproportionately much of one class subset. A staleness ceiling fixes it without a full barrier: a node whose pull is more than τ_max versions behind blocks until the laggards catch up, and everything inside the window behaves exactly as async does now.

This bounds the failure mode D5 only softens — with a ceiling, no update can become stale enough to be discounted into irrelevance in the first place. A gate on the existing pull path; the update rule itself doesn't change.

Touches: cofy/server.py (AsyncFedServer pull path), one new federation.max_staleness field

Ruled out, with the reason

  • Gossip / decentralized peer-to-peer averaging. Nodes would exchange weights directly with one another. Fails wall 1 at its core — the point is that nodes never address each other.
  • Partial participation / client sampling (standard FedAvg's own default). Structurally worse here than in ordinary non-IID FL: with one owner per class, skipping a node freezes every class it owns for that whole round. Sampling 2 of 4 WBC nodes leaves roughly half the classes with no updates at all.
  • Head personalization (FedPer and relatives). Nothing to add — the per-class head is already fully personalized under single ownership, as the measurement section establishes.

Track A — the one lever that adds signal rather than merging it better

Tracks M, D and S all make better use of the gradient signal that exists. This track is different: it is the only way to put gradient into the shared trunk for a class a node doesn't own — which is what the oracle gets for free on every image, and what no merge rule can manufacture. Both items respect all three walls.

A1
Give pseudo-labeling real box supervision, not just classification
low-moderate costnode-independent ✓the field report's own next step

No new information channel: the teacher's predictions for unowned classes come from real weight values other nodes already trained into the model this node legitimately downloaded. A node never needs to know what class 7 is called to use column 7's already-real detection score as a target.

The existing mechanism (cofy/pseudo_label.py, wired in client.py:165-287) pulls a teacher's raw per-anchor classification logits for unowned columns, thresholds them, and adds a soft BCE term — no NMS, no boxes, nothing reaching the TAL assigner. That's a weak signal, and it measured as one: enabling it landed statistically identical to off, 0.308 vs. 0.316 mAP50. The field report's own conclusion was to give the teacher's confident detections real box+class pseudo-targets through the normal assignment path instead.

Concretely: run the teacher through NMS for unowned classes on this node's own images above conf_thresh, inject the survivors as extra GT entries before the assigner runs, and weight their contribution to classification and box/DFL loss by pseudo_label.weight. Currently the box and DFL losses never fire on an unowned-class object at all, so this is the only proposal here that changes that.

Touches: cofy/pseudo_label.py, cofy/client.py:165-287 · reuses existing config knobs
A2
Fix the teacher so async's self-distillation isn't self-defeating
low costnode-independent ✓bug-adjacent, worth doing regardless of A1

Confirmed asymmetry: sync's teacher (server.py:211-223) is the global model as of one full round before the student's starting point — a stale but genuinely independent signal. Async's (server.py:527-532) is pulled_sd, the same weights the student initializes from, so its distillation loss compares the student against a copy of itself at cycle start. Whatever signal A1 produces is diluted specifically under async until this is fixed.

Fix: keep a small ring buffer of recent aggregated snapshots on the async server and hand each pulling node a teacher from N cycles back rather than the one it's about to train from — restoring the temporal distance sync gets by construction.

Touches: cofy/server.py:527-532 (AsyncFedServer) · no config change needed
