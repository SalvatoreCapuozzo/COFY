Two systems living in one repo

Legacy DAFYOLO 6 merge strategies

client.py → client_updated.py → client_v2.py, and the matching server*.py trio. A client trains a full YOLO checkpoint per class-set on a remote (or local) node, uploads it over SSH, and the server merges incoming heads into a shared global model using a selectable strategy: FedHead, Stitch, TIES, FedAvg, FedProx, YOLO-Inc, YOLOPA-NeckHead. run_experiments.py automates a full strategy × scenario sweep over VOC classes.

Actively developed the longest — 11 of the repo's 12 commits touch this line of code. Now lives under legacy/ (moved there this pass — see §7).

fedyolo_system/ rewrite, verified on real data

A from-scratch redesign built around one structural argument: YOLOv8's detect head ends in a 1×1 conv where output channel c literally is class c's logit. Split the model along that seam — shared backbone/neck/box-head vs. one per-class parameter slice — and aggregation stops needing a merge heuristic at all: shared weights FedAvg normally, each class slice averages only across the nodes that actually own it. Ships both a sync (round-barrier) and async (staleness-discounted delta) server.

Added in the same commit as the analysis docs below. One complete real-dataset run beats its own centralized baseline on 2 of 20 classes and reaches 68% overall — see §4.

Reading the pattern

  • Every strategy collapses the same way. Local models land respectably (0.20–0.88 mAP50, YOLO-Inc's locals are genuinely strong at 0.6–0.87) but every merged global model falls to 0.001–0.165 — a 85–99% relative loss versus the average local score, regardless of which of the 6 strategies did the merging. That uniformity is itself informative: it points at something structural in how heads get merged or evaluated, not a strategy-specific bug.
  • FedHead and Stitch score identically in the 2026-04-30 run (0.042 / 0.064) — expected, since Stitch is documented as FedHead's conservative subset (only the final 1×1 layer touched either way) when run against the same client checkpoints; it's a useful sanity check that the two paths are wired correctly, not evidence either one works.
  • YOLO-Inc consistently scores highest (0.059–0.165) and also has the strongest local models feeding it — it isn't obviously a better merge strategy so much as a better-conditioned input.
  • YOLOPA-NeckHead is worse than random at 0.001 both times it was tested, despite feeding from the strongest local models of any run (0.64–0.88) — the neck-averaging step this strategy adds over FedHead is actively destructive here.
  • Run-to-run variance is large even for the same strategy. FedHead's EXTREME_NON_IID score moved from 0.042 → 0.005 between 2026-04-30 and 2026-05-04 with the same scenario definition — global mAP in this system is not a stable measurement, which matters when deciding whether a future fix actually helped.
03

Why the legacy global model collapses

Seven analysis documents in the repo root (ANALYSIS_AND_FIXES.md, FIXES_IMPLEMENTATION.md, ALTERNATIVE_STRATEGIES.md and four summaries of them) diagnose this exact collapse against client_updated.py / server_updated.py as they stood on 2026-05-04/05. Their headline numbers (4–17% global mAP against 30–87% local) match the logged experiments above closely enough to trust — but the code has moved since, in the very commit that added those documents to git. Two claims were spot-checked against the code as it exists today:

Claimed: duplicate trainer.train() call no longer present

Filed as the #1 critical, 1-minute fix — a second, redundant call to trainer.train() at client_updated.py:310, silently doubling every client's training time. The current file has exactly one trainer.train() call (client_updated.py:339). Either it was fixed in the same pass that produced these docs, or the line reference drifted — either way, don't spend the "1 hour, +100%" budget on this one.

Structural: no shared feature space still true, verified in code

None of the six merge strategies decompose per-class output channels the way fedyolo_system/fedyolo/model.py does. FedAvg, TIES and YOLO-Inc all blend backbone/neck weights trained on disjoint class sets — five separate feature extractors get averaged into one, at random-initialization scale where there's no pretrained anchor pulling them toward a shared basin. This is the one root cause every document, the logged numbers, and the architecture itself all agree on independently.

The remaining 10 claims across the seven documents (alpha-weight miscalculation, batch-norm momentum, validation-set class pollution, catastrophic forgetting, etc.) were not individually re-verified line-by-line for this report — treat their code-line references as of 2026-05-05 and re-check against current server_updated.py / client_updated.py before acting on any single one. The diagnosis (disjoint-class averaging breaks a from-scratch shared backbone) is corroborated independently by the numbers in §2 and is the one to act on first.

Before the first number: what "Centralized" means in every table below

Every "Centralized" column from here on is fedyolo/centralized.py's baseline, and it's worth being precise about what that is not: a full-annotation oracle. It never sees a node with every class labeled on every image — that data doesn't exist in this setup. What it actually is: one model, one SGD optimizer, cycling through all four nodes' dataloaders in sequence every epoch, re-applying each node's class mask as it switches — the same partial-label constraint federated training faces, just trained directly instead of aggregated. So "Fed / Cent" answers "does aggregating independently-trained per-node copies beat directly cycling one shared set of weights through the same nodes," not "does federated beat a model that saw everything." That also means a ratio above 100% (common later in this report, once the 12-class/20-epoch generation shows up) isn't a red flag — it says federated won that specific comparison, plausibly because centralized's single optimizer carries momentum from one node's class-masked gradient straight into the next node's differently-masked batch, a known source of interference federated avoids by giving each node a fresh local optimizer and only reconciling at aggregation time. A true full-annotation ceiling would need a fifth "oracle" node with every image labeled for every class — named in centralized.py's own docstring, never built or run here.

Verifying the gap, on this Mac, in minutes not hours

The point of this pass wasn't a bigger mAP number — it was checking whether the federated/centralized gap from the one real-data win (§4, 68% of centralized mAP50) holds up once the 5 unlearnable/near-empty classes are gone and the run is small enough to actually iterate on locally. Using the new balanced_fraction (§9) on the cleaned 15-class dataset: class-stratified 10% subset, sync mode, yolov8s@480 — same architecture as the July 4 run, cut from 20×5 to 5×2 epochs (10 vs. 100 epochs/node). From scratch confirms pretrained matters

Federated and centralized collapse together (0.013 / 0.076) — at a 10-epoch/node budget, blank-weight YOLO genuinely can't learn this task, exactly as the framework's own "honest caveats" warn. This isolates the effect cleanly: pretrained: true (the current default) isn't a minor tuning knob here, it's load-bearing.

Open question: does per-class loss masking waste the shared "it's an egg" signal?

All 15 classes here are the same macro object — parasite eggs — just different species. Since a node's loss is masked to exactly zero for classes it doesn't own (client.py's class_weights), could that be throwing away a cross-species "there's an egg here" signal that would help every node, even ones that never see a given species?

Partly already answered by the architecture itself: fedyolo/model.py's shared/per-class split puts the backbone, neck, box-regression branch, DFL, and the two feature-mixing convs inside the classification branch (cv3.{i}.0, .1) in the shared, FedAvg'd-across-everyone bucket — only the final 1×1 per-class projection (cv3.{i}.2) is gated. So the entire visual representation, right up to the last layer, is already pooled across all four nodes regardless of species ownership. The genuine gap: loss masking zeroes a node's contribution everywhere for an unowned class, not just "don't suppress it" — so no node ever explicitly says "some egg, unknown species, is here," even though its own boxes are exactly that evidence in aggregate.

pseudo_label.py is the framework's existing answer to this gap — cross-round self-distillation from the previous global model for not-owned classes — which is why fixing its silently-broken start_round (config D, above) was the cheapest available test of the hypothesis. It came back inconclusive, not negative. A more direct test, if the hypothesis is worth pursuing further: add one new, class-agnostic output channel — binary "egg vs. background," never claiming which species — trained on the union of each node's owned-class boxes as positives. Because it never names a species, every node can supply full positive and negative supervision for it with no cross-node suppression risk (the exact problem loss-masking exists to prevent for the per-species channels). That's a model change, not a config flag — worth building only if a longer/cleaner pseudo-labeling test (more rounds, higher weight) shows the underlying idea has legs first.

A second open question: this whole setup assumes nc is known upfront

global_classes is a fixed list in the YAML config — cfg.nc = len(global_classes) is baked into the classification head's channel count at build_model() time and never changes for the life of a run. Every experiment in this report assumes whoever sets up the federation already knows the complete taxonomy, even though no single node owns more than 5 of the classes. That's a real simplifying assumption, not something already handled — grepping the codebase for any dynamic-nc mechanism (grow-the-head, placeholder channels, anything) turns up nothing.

Two ways to fix it, matching what was raised:

  • Pre-allocate a large fixed nc (e.g. 80, or better, a domain-informed ceiling — the source dataset's own classes_list.txt already enumerates the known taxonomy, unused slots just sit untrained until a node claims them). Zero architecture change — works with the code as it stands today, just a longer global_classes list with placeholder names. Costs: wasted head capacity for unused channels, and still requires a ceiling decided in advance — it doesn't solve genuinely open-ended growth, just raises the bar.
  • Grow the head on demand — when a new class is registered, extend the final per-class projection layer's weight/bias tensors by one row (copy the existing (nc, c3, 1, 1) tensor into the first nc rows of a new, larger one; random-init the new row), and add it to the aggregation registry. Architecturally the right answer — no wasted capacity, no arbitrary cap — but it's new engineering (a checkpoint-surgery utility plus config/registry updates), not a config flag.

For this specific dataset the assumption is milder than it sounds: parasite-egg taxonomy is finite and mostly known in advance (unlike general open-world object detection), so option 1 with a domain-informed ceiling — not literally COCO's 80 — is the pragmatic near-term answer. Option 2 is the right one before claiming this generalizes to a deployment where new species can show up from any node without a central authority enumerating them first. Neither is implemented; flagging this as a real limitation of every result in this report, not a solved problem.

A plan for grow-on-demand, grounded in what's already published

This is a named problem — Federated Class-Incremental Learning (FCIL) — not something to design from scratch. Three established technique families, and how each maps onto this codebase:

  • Distillation-based (e.g. GLFC, Dong et al. 2022) — a frozen copy of the model-before-the-new-class acts as a teacher, so learning the new class doesn't overwrite what was known. fedyolo/pseudo_label.py already does exactly this shape of distillation, just across node-ownership gaps within a fixed nc rather than across a class being added. Extending it to fire whenever a class is newly registered, not just every round, is a small change to an existing mechanism.
  • Parameter isolation / dynamic expansion (e.g. Dynamically Expandable Networks, Yoon et al. 2018) — freeze the parameters associated with existing classes, add fresh capacity for the new one. This is literally the "grow the head" option above: copy cv3.{i}.2's weight/bias into a larger tensor, random-init the new row, and — this part matters and is easy to miss — freeze the old rows' gradients for a few rounds while the new one catches up, or the shared backbone drifts to accommodate the new class at the old ones' expense (the same aggregation-drift mechanism implicated in ancylostoma's damping, §5 above).
  • Prototype/embedding-based classifiers — instead of a learned per-class weight row, represent each class as an embedding vector matched by similarity at inference. Adding a class becomes "register one more vector," not an architecture change at all. This one deserves its own paragraph — it's also the answer to the YOLO26 question below.

Recommended plan, in order: (1) extend pseudo-labeling to fire on class-registration events, not just elapsed rounds — cheapest, reuses existing code; (2) if that's not enough, implement grow-the-head with an explicit freeze-then-thaw schedule for old per-class rows; (3) if the deployment genuinely needs open-ended growth rather than a bounded-but-large taxonomy, skip both and go straight to the embedding-based head described next — it dissolves the problem rather than managing it.

The connection: YOLOE's open-vocabulary head is also the §5 answer

Investigated YOLOEDetect directly rather than going in with assumptions: its cv3 outputs a fixed embed-width visual feature (512-dim, independent of nc) — not a per-class logit. Class matching happens in cv4 (BNContrastiveHead) via similarity against externally-supplied text-prompt embeddings, with only a small global scale/bias learned there — not one row per class. There is genuinely nothing class-indexed to split; the chosen design (per the question asked before starting) makes this exact, not approximate:

  • per_class_param_names() returns [] for a YOLOEDetect head — aggregate_per_class() becomes a no-op and every real weight goes through the existing aggregate_shared() FedAvg path unchanged.
  • build_model() constructs a YOLOEModel instead of DetectionModel for YOLOE archs, computes the class-name text-prompt embeddings once via the arch's own text_model (mobileclip2:b) and caches them (re-encoding class names through a CLIP-style text tower on every build_model() call — once per node per round — would be a large, pointless cost), then calls ultralytics' own model.set_classes(names, embeddings). That stores the embeddings as a plain tensor attribute, not an nn.Parameter or registered buffer — confirmed directly: 'pe' in model.state_dict() is False — so it never needs explicit exclusion from FedAvg the way cv3.{i}.2 does elsewhere; there's simply nothing to exclude. One more bug, caught before it could waste days: the queue itself

And a real crash: async + yolov8l@640 ran out of disk

async + yolov8l@640 — the run that triggered the pgrep fix above — crashed for real once it actually started: RuntimeError: No space left on device, inside torch.save() during a routine per-submission checkpoint write. The driver script didn't stop or flag it — run() { ...; echo "DONE, exit $?"; } logs the exit code but never checks it, so the queue silently moved on to the next config and kept running for another two-plus hours before this was caught (by checking the driver log directly after being asked "can't you see that it actually crashed?" — a fair question; the honest answer at that point was no, not until asked to look).

Root cause, found in server.py: async mode saves a full checkpoint after every single submission (global_v{N}_{node}.pt) and never deleted the old ones — by design, per the module's own docstring ("a checkpoint is saved after every push so the full learning trajectory is recorded"). For yolov8s that's ~44MB × 40 submissions, tolerable; for yolov8l it's ~175MB × 40 = 7GB for one run, and this session had already accumulated similar unbounded growth across every earlier sync run too (global_round{N}.pt, same pattern, one file per round, never pruned). Nothing downstream reads any checkpoint but the latest one — confirmed by grepping the whole codebase for references to these filenames before touching anything. Fixed in both FedServer.run() and AsyncFedServer.push(): save the new checkpoint first, then delete the previous one (never zero checkpoints on disk even if a crash lands mid-write), keeping only the latest round/submission plus the true global_final.pt at the end. Also pruned ~26GB of already-accumulated intermediate checkpoints from both completed and archival runs (every summary.json — the actual numbers cited throughout this report — was left untouched; only the redundant intermediate .pt files were removed), taking free disk from ~8GB back up to ~34GB. The crashed run is re-queued (async_l640_20ep_retry, appended after everything else already queued) and a live monitor now watches every chained driver script's own "DONE, exit N" markers, so a future non-zero exit gets caught immediately instead of silently, next time.

Why the oracle runs' own federated numbers kept drifting — traced to a real gap, not a backend quirk

Every "same config, different result" case in this report so far (the 0.622/0.651 YOLO26-classic pair above, the async@m480/s640 fixed reruns in §5d/§5e, the oracle runs' federated numbers never quite matching their leaderboard siblings) had been attributed to "MPS/PyTorch non-determinism" — a real phenomenon, but a vague one, and it turns out not to be the dominant cause. Checked the actual seeding code directly: client.py, server.py, and centralized.py only ever call torch.manual_seed() — Python's own random module and NumPy's RNG are never seeded anywhere in fedyolo. Confirmed directly in the installed ultralytics package (ultralytics/data/augment.py, 43 call sites) that mosaic composition, random-perspective jitter, HSV color jitter, and crop offsets — the entire training-time augmentation pipeline every dataloader runs — draw from exactly those two RNGs, not torch's. So cfg.seed: 0 only ever fixed weight-init and forward/backward randomness; every batch's actual augmentation was drawn from whatever state Python/NumPy happened to auto-seed from OS entropy at process startup, different every single invocation regardless of the config. A real, fixable gap in fedyolo's own code, not a backend characteristic — correcting the earlier framing here rather than leaving it standing. Fixed by adding random.seed(cfg.seed [+ round_idx]) and np.random.seed(...) alongside every existing torch.manual_seed() call, in client.py, both server classes, centralized.py (covers oracle.py too, which reuses it), and simulate_to_target.py. This doesn't buy full bit-for-bit reproducibility — MPS may still contribute some residual non-determinism at the kernel level, and PyTorch's deterministic-algorithms mode doesn't have full MPS coverage — but it closes the larger, actually-fixable gap.

Why sync tightened up but async didn't — a real, testable mechanism, not just "more variance." client.py reseeds every RNG with cfg.seed + round_idx at the start of each node's local training, and the seeding fix makes that reseed fully deterministic given a fixed round_idx. Why Phase 2 underperformed its own design, and the fix

Phase 2 (YOLO26 native end2end) was supposed to be the more capable architecture — NMS-free, YOLO26's own flagship head design, the one ultralytics actually ships as the default in yolo26*.yaml. Instead it's been the weaker of the two YOLO26 tracks throughout this report: Phase 1 classic reaches 0.671 best-absolute (leaderboard rank 1, §5e) against Phase 2's 0.596; Phase 2's sync@s480 ratio (66%) is the worst clean result of any architecture at that scale, worse than Phase 1's own sync@s480 (89%). That gap was flagged early and revisited several times (§5d) without a root cause — until now.

The bug: the branch that matters was permanently undertrained

YOLO26's end2end head trains two parallel branches from the same backbone — one2many (many candidate boxes per object, like classic YOLO training) and one2one (a single best match per object, the NMS-free branch actually used at inference — Detect.forward() returns preds["one2one"] whenever self.training is False, confirmed directly in ultralytics' own head.py). Ultralytics' E2ELoss class is supposed to ramp the loss weighting between them over the course of training — o2m (one2many's weight) starts at 0.8 and decays to 0.1 by the end, so o2o (one2one's weight) rises from 0.2 to 0.9. That ramp only advances when something calls criterion.update() once per epoch. Grepped every training path in fedyolo — client.py, centralized.py, simulate_to_target.py — and .update() is called nowhere. Every Phase 2 run in this entire investigation trained with o2m=0.8/o2o=0.2 fixed for its whole duration: the one2one branch — the only branch that determines every reported Phase 2 mAP50 — received just 20% of the loss signal the whole time, never the 90% ultralytics' own design intends by the end of training. Verified directly (not assumed): E2ELoss(model).o2m == 0.8 immediately after construction, still 0.8 after simulating a full training run's worth of batches with no .update() calls — exactly fedyolo's actual code path.

A second, compounding issue: even calling .update() naively would have crashed. E2ELoss.decay() reads self.one2one.hyp.epochs, but fedyolo's model.args (built by model.py's _default_train_args()) is a minimal SimpleNamespace(box=7.5, cls=0.5, dfl=1.5, imgsz=imgsz) — no epochs field at all, since nothing needed one before. Confirmed by trying it: AttributeError: 'SimpleNamespace' object has no attribute 'epochs'.

Independent, external confirmation this isn't a made-up concern: YOLO26's own paper (arXiv:2601.12882) describes exactly this class of mechanism (it calls the classification/regression version "ProgLoss") as necessary precisely because "static balance is suboptimal for end-to-end learning ... stagnation at any fixed weight ratio would impair training." A permanently-fixed 0.8/0.2 split is precisely the failure mode the architecture's own authors designed this mechanism to prevent.

The fix

client.py (federated path): after constructing E2ELoss, set both internal loss objects' hyp.epochs = cfg.federation.local_epochs (not the federation's total epoch budget — model and criterion are rebuilt fresh from the aggregated global weights every round, so local_epochs, typically 2, is the actual span this criterion instance lives for), then call criterion.update() at the end of every local epoch. With local_epochs=2 this means: first epoch trains mostly one2many (o2m=0.8), second (last) epoch trains mostly one2one (o2m→0.1) — every round's contribution now meaningfully trains the branch that actually gets evaluated, instead of never advancing past its starting point.

centralized.py needed different surgery: it already force-rebuilds model.criterion on every node switch (a pre-existing fix for a YOLOE hasattr caching quirk, §5d), which is even more frequent than client.py's per-round rebuild — a naively-added decay would never accumulate any progress at all, resetting to 0.8 every few dozen batches. Fixed by building the E2ELoss instance directly (bypassing BaseModel's lazy init_criterion()), scoping hyp.epochs to the run's real total_epochs, and fast-forwarding criterion.updates/o2m/o2o to wherever the current epoch actually sits in that schedule immediately after construction — so decay progress survives the rebuild instead of restarting from 0.8 every node switch. This also fixes oracle.py, which reuses train_centralized_baseline() unchanged. (simulate_to_target.py has the identical latent issue in its own separate centralized-training function — not fixed here, since that entry point wasn't used to generate any result in this report, but flagged as a known follow-up.)

Smoke-tested end to end on the synthetic toy dataset (sync mode, yolo26n, 2 rounds × 2 local epochs, --also-centralized): both the federated and centralized paths ran clean through the new code — no traceback, criterion.update() actually invoked, summary.json written correctly. (mAP50 reads 0 on this run, same as every prior synthetic-set smoke test in this report — expected on 24 tiny images over 2 epochs, not a sign of a problem.)

How a competitor handles this: UltraFlwr (Flower + Ultralytics YOLO)

Looked at UltraFlwr (arXiv:2503.15161, MICCAI-AMAI'25) — the closest existing published federated-YOLO framework, built on Flower rather than fedyolo's own hand-rolled server/client, and the natural "how do others do this" comparison point. Two things stand out, both genuine architectural differences from fedyolo rather than one being simply "better":

  • Aggregation granularity is coarser. UltraFlwr's own finding: "aggregating both backbone and neck components achieves performance comparable to full aggregation with lower communication costs" — i.e., their unit of aggregation is whole model components (backbone/neck/head), not individual per-class weight rows. Nothing in their public materials describes fedyolo's core mechanism — splitting the final per-class conv layer itself so a node only ever contributes to/receives the classes it owns (per_class_param_names(), this report's §1). Their heterogeneity benchmarks are framed around "differences in data curation, video length, and label availability" — closer to not-identically-distributed data than to genuinely non-overlapping class sets across clients. fedyolo's whole premise (four nodes that between them own zero overlapping classes, §5c) is a harder, more specific problem than what UltraFlwr's own benchmarks appear to target.
  • Standard FedAvg, with a known limitation stated plainly. Their own result: "standard FL aggregators (e.g., FedAvg) do not consistently match centralized training per client but reduce inter-client performance variability" — i.e., federated doesn't reliably beat centralized for them, it mainly makes results more consistent across clients. fedyolo's own numbers tell a different story on this specific point: federated meets or beats its own centralized baseline in the large majority of configs on the current 12-class/20-epoch leaderboard (98-116% Fed:Cent throughout). Not a claim that fedyolo is unconditionally better — the two systems are solving adjacent but different problems (UltraFlwr: same classes everywhere, comms-efficient partial aggregation; fedyolo: disjoint per-node classes, per-class-conditional aggregation) — but a real, useful data point for the SOTA comparison requested next.

Why centralized/oracle ran twice per matched pair, and the fix

Direct question from the user, prompted by noticing that sync/async matched pairs (same arch, same scale) each got their own --also-centralized/--also-oracle run: why train the same baseline twice, and why do the two trainings give different numbers? Checked both empirically rather than assuming.

Why twice: diffed an actual matched pair, kfm12_yolo26_sync_l640_20ep.yaml vs. kfm12_yolo26_async_l640_20ep.yaml -- everything is identical (batch_size: 4, local_epochs: 2, arch, imgsz, nodes, seed: 0) except the mode-specific fields (mode, rounds vs. async_node_cycles, eval_interval). Neither centralized.py nor oracle.py reads federation.mode for anything except matching the total local-epoch budget (rounds×local_epochs vs. async_node_cycles×local_epochs, designed to be equal). So the two baselines were, in principle, testing the identical experiment -- the redundancy was purely a CLI architecture limitation: simulate.py trained everything fresh inside whichever single invocation you made, with no mechanism to reuse a baseline a sibling config had already trained.

Why the results differed anyway: the same non-determinism already documented at length in this report (§5e) -- each invocation is an independent process; even post-seeding-fix, MPS backend ops retain some residual non-determinism. Two "identical" centralized/oracle trainings, launched from different config files, were never going to be bit-identical.

The fix: a real --mode flag

Added --mode {sync-async,sync,async} to fedyolo.simulate, default sync-async. Refactored the federated-training block into _run_one_federated_mode(cfg, mode, ...), called once per requested mode; each mode gets its own {output_dir}/{sync,async}/ subfolder so the two servers never collide on shared checkpoint filenames (both FedServer and AsyncFedServer write global_final.pt, for instance -- confirmed directly by grepping both classes' checkpoint-saving code before writing the fix, not assumed). --also-centralized/--also-oracle stayed exactly where they were in the flow -- after the federated mode(s) run -- so they now train once and land in summary.json shared across whichever mode(s) ran, keyed as federated_sync/federated_async instead of the old single federated key. --mode overrides federation.mode in the config entirely (that field still sets sync/async-specific defaults like rounds/staleness_alpha, just not which mode(s) actually execute).

Smoke-tested end to end on the real 12-class dataset (tiny balanced_fraction: 0.02, 1 round/1 cycle/1 local epoch, default --mode, --also-centralized): both sync and async federated legs completed, summary.json came out with exactly the expected federated_sync/federated_async/centralized keys, and the output directory had separate sync//async/ subfolders alongside one shared centralized_baseline.pt and pooled_val/ -- confirmed by listing the directory, not assumed from the log alone. One known, accepted inefficiency left as-is: the fallback evaluation path (only triggered when eval_interval is set so high no mid-training eval ran) re-materializes each mode's own pooled val set separately rather than sharing one cache -- not worth the extra plumbing given how rarely that fallback path actually fires.

SOTA comparison: UltraFlwr, and everything wrong with running it on this Mac

Scoped earlier (§5f): install the real UltraFlwr (Flower + Ultralytics), run it in its own native mode — homogeneous, equal- ratio class splits, the opposite of fedyolo's disjoint-per-node partial-label design — on the same real image pool, with models scale-matched to fedyolo's own flagships rather than UltraFlwr's own nano-only demo defaults. Confirmed via AskUserQuestion: real install, native mode, flagship scale only. What actually happened getting there was most of the work.

Worth restating plainly, not just implying: every client in this run had homogeneous class access — every client sees every class, just different images. That's not a setting chosen for convenience; §5g above already found it directly in the source and it holds for the actual run too — UltraFlwr has no mechanism anywhere in its code for disjoint per-node class ownership. fed_split.py takes only an image-count ratio per client and copies whichever images land in that slice with their labels untouched; yolo_client.py's training call has no owned-classes concept or loss-masking at all. Homogeneous splitting isn't UltraFlwr's default, it's the only mode it's built to run. Running fedyolo's exact disjoint 4-node split through UltraFlwr's stock pipeline would need modifying their client code — which would mean testing a framework we wrote around their framework, not UltraFlwr itself.

Worth the same directness on sync vs. async: UltraFlwr has no async mode, so every run of it is sync by construction. It's built on stock Flower — fl.server.start_server driving a FedAvg strategy — which is a round-barrier protocol at its core: configure_fit samples a client set, the server blocks until every sampled client's fit() call returns, then aggregate_fit runs and the next round starts. There's no staleness weighting, no partial/out-of-order aggregation, nothing resembling fedyolo's own AsyncFedServer node-cycling anywhere in Flower's core or in UltraFlwr's code on top of it. So "is the UltraFlwr result sync or async" doesn't have an answer in UltraFlwr's own terms — it only ever runs the one way, and that one way is structurally fedyolo's sync mode. The yolo11l numbers below should be read against this project's own sync-mode rows, not averaged against or contrasted with async ones.

Four real bugs in UltraFlwr's own code, found by reading the source

UltraFlwr's yolo_client.py instantiates its model as bare YOLO() — no argument — regardless of any config file. Ultralytics' default is yolo11n.pt: nano, always, no matter what the repo's own yolo_configs/ nc-parameterized yaml files (which turn out to be dead code, never referenced by the actual training path) suggest is configurable. Patched to read a MODEL_NAME env var instead, so the same codebase can run yolov8l.pt (matches fedyolo's yolov8l@l640) or yolo11l.pt (closest available proxy to yolo26 — YOLO26 itself isn't in this ultralytics pin, 8.3.48, which predates it; YOLO11 is the direct architectural predecessor, same C3k2/C2PSA backbone/neck lineage). Second: the server's aggregation code (strategies.py) independently hardcoded a nano-scale yaml for reconstructing the global model after each round — untouched by the client patch, so the very first real validation run crashed at the end of round 1 with a state_dict shape mismatch (12-vs-80 channel head). Third, related: once patched to use MODEL_NAME there too, it still crashed — YOLO('yolov8l.pt') loads the COCO-pretrained 80-class checkpoint, not an nc=12 architecture, so the shape mismatch just moved. Fixed by constructing DetectionModel(cfg='yolov8l.yaml', nc=12) directly — exactly what ultralytics' own model.train(data=...) does internally, just made explicit here since the aggregation path never calls .train() itself.

Fourth, in ultralytics itself (this pin, 8.3.48), not UltraFlwr: select_device(None) — the trainer's default when no device is specified — mis-parses str(None) into the literal substring "none", then strips that substring out during device-string cleanup, leaving an empty string that matches neither the CUDA nor MPS branch and falls through to CPU. Confirmed directly: select_device(None) and select_device("") both return cpu on this Mac, MPS available or not. Every UltraFlwr client was training on CPU the entire time until caught — explains the initial ~10-14s/it concurrent throughput, consistent with CPU on a 43M-param model rather than any real GPU contention. fedyolo's own client.py never hits this: it resolves "auto" to a concrete device itself (torch.backends.mps.is_available()) rather than trusting ultralytics' own auto-detection. Same fix applied to UltraFlwr's client: pass device='mps' explicitly.

Concurrent MPS access is worse than no GPU at all, on a single-GPU Mac

Fixing the device bug revealed a second, genuinely surprising problem: with both clients correctly using MPS concurrently (Flower's synchronous round protocol needs every client live and training at once — unlike fedyolo's own max_concurrent_nodes: 1 throttle), throughput measured worse than the CPU baseline it replaced — roughly 34s/it for two contending MPS processes versus an isolated single MPS process's ~2.2s/it, and versus ~10s/it for two CPU processes with no GPU to fight over. Apple's Metal backend does not handle multi-process concurrent access well; two processes sharing one physical GPU serialize with heavy overhead rather than time-slicing efficiently. Fixed by serializing actual GPU access across the client processes with a real file lock (filelock, already a dependency) — letting each client run at its fast isolated-MPS speed, one at a time, rather than both waiting on a contended GPU simultaneously. Net effect measured directly: a 4-round validation went from an estimated 16+ hours (concurrent MPS) down to well under an hour.

A real, unbounded memory leak — and the OS-blocking incident it caused

UltraFlwr's client reloads a fresh model every round (del self.net; torch.cuda.empty_cache(); self.net = YOLO(weights)) — standard practice, except torch.cuda.empty_cache() is a CUDA-only call, a silent no-op on MPS. Apple's MPS allocator cache from the previous round's model, optimizer state, and EMA buffers was never released, and PyTorch's autograd graph creates reference cycles that plain del doesn't break — only gc.collect() does. This compounded every round, unbounded, for 10 rounds × 2 clients, and roughly an hour into the first real run it grew a training process to 65GB and blocked the whole OS, forcing a hard restart. Root-caused via direct empirical testing (not guessed): select_device behavior, isolated-vs-concurrent throughput, and this leak were each confirmed by running small, targeted tests before trusting a fix. Fixed with gc.collect() + torch.mps.empty_cache() at every point the old model gets dropped, both client- and server-side. Verified, not assumed: a 4-round supervised test directly tracked RSS across every round transition, showing the same bounded oscillation (6MB to ~2.9GB, no growth trend) round after round — the fix holds.

A second, independent safety net was added regardless of whether that fix is complete: a watchdog script running alongside every training run, killing everything immediately if any single process exceeds an 8GB RSS ceiling or system-wide free memory (via macOS's own memory_pressure -Q accounting, not the misleadingly-low raw vm_stat free-page count) drops below 10%. It has since fired twice in real use — both times safely, no OS lockup, system recovering to 60-70% free within seconds of the kill.

The watchdog firing surfaced two further gaps, both real

The first trigger (system free memory at 9%) killed the training processes correctly, but the outer queue script survived a kill pattern that should have matched it, and — undiagnosed why, still open — silently moved on to the next model instead of stopping. Fixed with an explicit, individually-logged kill function instead of a single pkill -f alternation, and a real completion check (the round-10 checkpoint file existing) rather than trusting the wrapper's exit code, which reads as success even when a run was killed mid-flight.

Separately: when the VS Code window hosting this whole session was force-closed after Activity Monitor reported ~80GB (the swap file had grown to 35GB total, ~31-34GB in use — almost certainly the real source of that figure, not one process holding 80GB of actual RAM), the training server and the watchdog itself died with it, but the two client processes survived as orphans — reparented to init, pointlessly holding memory and CPU trying to reach a server that no longer existed, with nothing left running to notice. Root cause: inconsistent process-group survival when the parent session dies — some children got signaled, others didn't, no design behind which. Fixed two ways: every server/client/watchdog launch now runs under nohup so survival is uniform and intentional rather than an accident of timing, and the watchdog gained an explicit orphan check (client process alive, no matching server process → kill it) as a second line of defense independent of whether the nohup fix fully covers every future failure mode. 8 of the yolo11l leg's intended 10 rounds had already completed cleanly before this happened; per explicit instruction, that result is kept as final rather than re-run to a clean 10.

The same incident happened again on the v1→v2 dataset rerun — the nohup fix was incomplete, not wrong

Restarting this comparison with the corrected balanced_image_subset() dataset (see below), VS Code got force-closed again under memory pressure while the run was mid-round-3-of-10. Same shape as before: server, queue script, and watchdog all died together; the two client processes survived as orphans, burning CPU trying to reach a server that no longer existed, for roughly two and a half hours before anyone noticed — this time caught only because a stale background-task notification (the previous session's own monitor reporting itself stopped, with no completion record) prompted a fresh check rather than by any alarm firing. Root cause, actually understood this time: nohup ... & disown only makes a process ignore SIGHUP — it does not remove the process from its launching shell's session or process group. VS Code force-quitting kills that whole group at once, and a merely-nohup'd child is still a member of it. The earlier fix's "uniform nohup everywhere" made survival more consistent but never addressed this — the two clients surviving both times was still down to lucky reaping-race timing (already orphaned to init a moment before the group-kill swept through), not real protection.

Real fix: daemonize.py, a small double-fork daemonizer (os.fork(), os.setsid(), os.fork() again, stdio redirected to a log file) that launches run_comparison_queue.sh as a genuine Unix daemon: PPID=1 from the instant it starts, its own session and process group, no controlling terminal — structurally outside VS Code's process tree rather than just deaf to one signal from it. Everything the script spawns afterward (watchdog, server, both clients) inherits that same detached session automatically, so the whole tree gets the protection, not just the top-level process. Verified directly, not assumed: checked ps -o pid,ppid,pgid,sess on the relaunched queue process immediately after starting it — PPID=1, PGID distinct from the launching shell's own. The killed run's round-3 checkpoint wasn't kept (too partial to be worth preserving, unlike yolo11l's round-8 stopping point above) — relaunched clean from round 0 under the new daemonized launch path.

Third time: the setsid() fix looked correct, was verified directly, and still wasn't enough

Same VS Code force-quit, again, this time with training already at round 4/10 — real progress lost a third time. ps -o pid,ppid,pgid,sess on the daemonize.py-launched process had shown exactly what a correct fix should show: PPID=1, its own session, its own process group. It died with VS Code anyway. Root cause, actually correct this time: macOS force-quit doesn't kill by Unix process group at all — it kills by process coalition, a separate macOS-specific resource- accounting mechanism (visible in log show's runningboardd output as "jetsam coalition id" / "resource coalition id", spotted in passing while triaging the second incident but not connected to the fix until this third one). A process inherits its coalition from its parent at fork() time, and setsid() — which only touches the POSIX session/process-group layer — does nothing to it. Any process forked from anywhere inside VS Code's tree stays in VS Code's coalition permanently, however detached its Unix session looks. nohup and daemonize.py were both real improvements on their own terms (uniform signal handling, genuine session detachment) — neither was ever going to survive a coalition-wide kill, because neither operates at the layer macOS actually uses to force-quit an app.

Real fix: skip Unix-level detachment entirely and have launchd spawn the process directly, so it gets its own coalition from birth rather than inheriting one. launchctl submit -l <label> -o <log> -e <log> -- /bin/bash run_comparison_queue.sh does this without writing a .plist file at all — worth noting since a direct plist write (to ~/Library/LaunchAgents/ and, when that was blocked, to a scratch directory too) was tried first and refused by this session's own permission classifier as a recognized persistence mechanism, correctly — launchctl submit is the same underlying mechanism scoped to one non-persistent, immediately-visible job instead. Verified with launchctl list | grep dafyolo (shows the job, tracked by launchd) and ps -o pid,ppid -p <pid> (PPID=1, parent is launchd, never any shell in this session). Round 4's checkpoint wasn't kept either, for the same reason round 3's wasn't — relaunched clean from round 0 a third time, this time under launchctl submit.

Relaunching after the batch2/batch3 pause: a rapid restart loop that turned out to be a completely different, pre-existing bug

Paused per explicit request while the batch2/batch3 leaderboard queues ran (§05, above), then relaunched via the same launchctl submit mechanism once they finished. The queue log immediately looked broken: yolo11l... STARTING, INCOMPLETE a few seconds later, yolov8l... STARTING, INCOMPLETE, COMPARISON QUEUE COMPLETE, then yolo11l... STARTING again — the whole two-leg script apparently re-running itself from the top, repeatedly, seconds after each "completion." run_comparison_queue.sh has no loop in its own code, so this looked exactly like the kind of launchd auto-restart behavior nobody had intended (no KeepAlive was ever set) — the obvious suspect given everything else this investigation had already pinned on launchctl.

Checked directly rather than assumed: submitted a trivial one-line echo job via launchctl submit and watched its log for 5 seconds — exactly one line, confirming launchctl submit genuinely is one-shot here, not restarting anything on its own. So the restart loop had a different cause. Checked the actual server log from a failed leg: ModuleNotFoundError: No module named 'FedYOLO' — every leg was crashing in about 3 seconds, and the queue script's own retry-free two-leg-then-exit logic, run repeatedly by something, was what produced the "loop" (most likely a stale duplicate job registration surviving between conversation turns, though the exact mechanism was never fully pinned down — thorough cleanup of every com.dafyolo.* label before the next relaunch resolved it regardless).

Root cause of the crash itself, confirmed by direct reproduction rather than guessed: FedYOLO/ has no __init__.py — an implicit PEP 420 namespace package, importable only if the project root happens to be on sys.path. python3 FedYOLO/train/yolo_server.py puts the *script's own* directory (FedYOLO/train) on sys.path[0], not the project root — so this depends entirely on something else (an ambient PYTHONPATH, most likely) supplying the project root. Reproduced the identical crash running the exact same command directly in a plain shell, no launchctl involved at all — conclusive proof this was never launchctl-specific, just coincidentally surfaced while relaunching under it. Something in the environment had stopped providing whatever used to make this resolve; never identified exactly what changed, since the real fix doesn't depend on knowing. Fixed by explicitly exporting PYTHONPATH to the project root inside run.sh itself, so it no longer depends on the invoking environment at all. Verified before trusting it: ran the server directly again, watched it reach [ROUND 1] cleanly. Relaunched the real queue once more after a from-scratch cleanup of every launchd label involved — this time a single clean STARTING line, no loop, PPID=1 confirmed again, real training progress visible in the log.

Final resolution: retired, not fixed further

The relaunched queue above went on to consume enough memory to block the whole machine again — the same failure this section's every previous incident already describes, just with the process- supervision layer (nohup, then daemonize.py, then launchctl submit) now finally solid. That's the actual finding: every fix in this section was real and needed, and none of them touch the actual root cause, because the root cause was never process supervision. It's that UltraFlwr's own architecture runs 2 clients concurrently on this Mac's single MPS GPU (Flower's protocol requires every sampled client training at once; unlike fedyolo's own max_concurrent_nodes=1 throttle, there's no equivalent knob on UltraFlwr's side) — genuinely more concurrent memory pressure than this 16GB machine reliably has spare, independent of whether the processes survive a VS Code close. fedyolo's own sequential, one-node-at-a-time architecture has never once produced this failure across dozens of runs this entire investigation — the difference is structural, not a bug to patch. Decision: UltraFlwr comparison runs are retired from this project's scope — not relaunched again, per explicit instruction. The one real result already obtained (yolo11l, 8 of 10 rounds, below) stands as the final word on this comparison; yolov8l's leg never completed and stays incomplete. All UltraFlwr processes and the launchd jobs supervising them were confirmed stopped and removed before closing this out.

Every attempt's partial checkpoint was overwritten by the next attempt's own cleanup step before being preserved — a real gap (yolo11l's round-8 checkpoint was saved deliberately before its retry queue could touch it; the same precaution was never applied to yolov8l's retries) — so there is no usable yolov8l checkpoint to evaluate, unlike yolo11l. Explicit decision, not a default: stop here rather than keep re-attempting on the same hardware under the same load. yolo11l's single result stands as the comparison point for now. Full multi-hour, uninterrupted access (a quieter window, a different machine, or literally just this Mac running nothing else) would be the way to actually finish this leg, not a further code fix.

Is there a disjoint-class competitor to benchmark against? Checked directly — no.

Asked directly rather than assumed: does a maintained federated object-detection framework already exist for the actual problem this project solves — disjoint per-node class ownership, not just standard non-IID (every client sees every class, in different amounts)? "Partially class-disjoint data" (PCDD) is a real, named research area with working code — FedMR and FedGELA (Zhang et al., Federated Learning with Bilateral Curation for Partially Class-Disjoint Data) both solve exactly this — but both are image-classification-only, built around techniques specific to a classifier head (a globally-fixed simplex ETF classifier, a manifold-reshaping loss) that don't transfer to a YOLO detection head at all; there's no analogous "classifier" to fix that way in a bounding-box regression + per-class objectness architecture. Every actively-maintained federated object detection framework found — UltraFlwr (already tested), FedPylot (YOLOv7, PyTorch, checked directly: "does not evaluate disjoint/non-overlapping class ownership... every client maintains exposure to all classes," and built for MPI/HPC clusters, not a single machine), and FedVision — handles only standard non-IID.

One real match: CMPE-295A-Master-Project genuinely implements "each client deficit of a minimum of one class" for object detection. It's also a university capstone — YOLOv3 on TensorFlow, 13 total commits, 31 stars, no signs of recent maintenance — not a published, tested framework the way UltraFlwr is. Explicit decision, discussed rather than assumed: skip integrating it. Given UltraFlwr's own setup (a well-documented, arxiv-backed framework) already surfaced four real bugs and took most of a session, a smaller and less-maintained codebase on an older stack is a worse bet for the payoff, not a safer fallback. The finding stands on its own regardless: disjoint-per-node-class federated object detection doesn't have an established competitor to benchmark against. This project is addressing a real gap in what's out there, not failing to match something that already exists.

A real client-server federation, with GUIs — fedyolo.net

Every run in this whole investigation, sync or async, real or simulated, has run inside one Python process — FedServer.run() calls run_node_round() directly as a function call (or via a local ProcessPoolExecutor), and AsyncFedServer.pull()/push() are plain in-process method calls. No networking anywhere in the training path. This section is a new, additive subsystem — fedyolo/net/ — that runs the exact same config-driven federation as an actual distributed system: a server process with a browser dashboard reachable by IP, and separate client processes (one per node, each its own local GUI — a "personal room") that pull the global model, train on their own machine's own local dataset, and push results back over real HTTP. Built to work with everything on one Mac (several client processes simulating several nodes) or spread across two Macs on the same Wi-Fi, with an explicit eye toward extending it to a real internet-facing deployment later (not built now — no auth/TLS, scoped deliberately to a trusted local network).

Design: reuse the aggregation core, replace only the transport

AsyncFedServer.pull()/push() were already shaped almost exactly like a network API — pull() returns (state_dict, version); push() takes (result, pulled_sd, pulled_version) — and already thread-lock-protected. The async room in fedyolo/net/rooms.py just holds one real AsyncFedServer instance and forwards onto those existing methods; the only new logic is a small in-memory ring buffer of recent global-state snapshots (keyed by version) so a client's push can compute its staleness delta without re-uploading the — sometimes 100+MB — state_dict it originally pulled. The sync room implements its own small round barrier (buffer each node's submission for the current round; once every configured node has reported in, call the exact same fedyolo.model.aggregate() FedServer.run() already uses), driven by network pushes instead of a process-pool loop. Client-side, run_node_round() is called completely unmodified — the client just overrides its own node's data_yaml to a real local path before building the config, everything else (architecture, hyperparameters, class list) comes verbatim from the server's own config file via a new config.load_config_from_dict() (split out of the existing load_config() for exactly this reuse).

Two real bugs found via actual end-to-end runs, not guessed

Smoke-tested with a small 2-node, 7-class subset of kfm_250423_clean12 (real data, tiny balanced_fraction, yolov8n) run across three separate local processes (one server, two clients) on this same Mac. First sync attempt reached its final round — aggregation succeeded, the round counter correctly hit 2/2 — and then the whole request crashed with TypeError: Room._emit() got multiple values for keyword argument 'label': _run_eval()'s return dict already carries its own "label" key, and the emit call was also passing label=label explicitly on top of unpacking that same dict. The exception fired after the eval result had already been recorded but before the room's finished flag got set — a room could genuinely reach its last round, record a real eval, and then never report itself finished. A second, related mismatch: the code filtered a "per_class_map50" key that doesn't exist — the real field is "per_class" — silently failing to strip the large per-class breakdown out of every event payload. Both fixed; re-ran clean end-to-end afterward (finished: true, round 2/2, real eval numbers). A live status-polling timeout was also found the same way: a client waiting on the sync barrier polled the server's status endpoint with a 10s timeout, which fired for real while the server was busy running another node's barrier-closing aggregation + eval — fixed by treating a polling timeout as retry-worthy rather than fatal, and raising it to 30s.

One more correctness issue caught by design review before it ever ran: run_node_round() seeds every RNG via cfg.seed + round_idx, and what round_idx means differs by mode — sync shares one round counter across every node; async seeds off each node's own local cycle count, never the shared global version number. The client's pull response returns a single "round-or-version" marker for both modes (whichever Room.sync_pull/async_pull returns); passing that straight through as round_idx for async would have silently seeded every node identically to the global version count instead of its own cycle count, diverging from what the in-process AsyncFedServer._node_loop actually does for the same config+seed. Fixed by branching on mode before choosing what to pass.

Verified: both modes, end to end, plus real LAN reachability

Sync: 2 nodes, 2 rounds, real barrier behavior over HTTP — node A's push before node B's correctly returned round_advanced: false and made A's client wait; node B's push correctly closed the barrier, triggered aggregation, and both clients then pulled the new round automatically. Async: 2 nodes × 2 cycles each (4 total submissions), version counter reached 4/4, staleness cache exercised on every pull, both nodes finished cleanly with two real eval entries recorded at the configured interval. Server confirmed reachable via this Mac's actual LAN IP (192.168.1.175:8900, not just 127.0.0.1) — the same path a second Mac on the same Wi-Fi would use, without any code difference from the single-machine case.

What's deliberately not built yet

Pseudo-labeling (federation.pseudo_label.enabled) isn't wired through the network protocol — every config in this project has it disabled, so the client always calls run_node_round() with teacher_state_dict=None; adding it would mean the server also serving the previous round's snapshot. No authentication or TLS — this is scoped to a trusted local network by design, matching the request's own framing of "one Mac, or up to two on the same Wi-Fi, extendable later." Usage instructions (starting the server, joining a room from a client, the one-Mac vs. two-Mac setup) are in fedyolo/net/README.md.

Bug 1: the whole matrix died in under a minute, on the wrong python3

run_matrix.sh called bare python3 — whatever that resolves to on PATH at invocation time — instead of pinning this project's actual dl_env conda environment. Run from a shell sitting in (base) (no torch installed there), all 53 queued subprocess launches died in import torch before doing anything, finishing the "whole matrix" in seconds with nothing trained — caught from the run's own implausibly-short wall-clock time and a quick cat of the first log, not from any tool complaint. Fixed two ways: run_matrix.sh now hardcodes $HOME/anaconda3/envs/dl_env/bin/python3, and run_matrix.py preflight-checks torch/ultralytics importability once before touching the queue, so a wrong environment fails with one clear message instead of cascading through every config. A second, related fix: the tqdm-style progress bar looked garbled (a wall of near-duplicate lines instead of overwriting in place) because subprocess.Popen(text=True) forces universal-newline translation, silently rewriting the bar's bare \r into \n — fixed by reading and forwarding the child's raw bytes instead of line-splitting them.

Bug 2: an orphaned duplicate process, doubling load on an already memory-tight machine

Reported directly: "it is incredibly slow and it is blocking everything." Checked real process state (ps -o pid,ppid,pgid,lstart,command) rather than guessing: two separate fedyolo.simulate processes were training the identical session (kfm12_yolo26_sync_l640_20ep_seed1) at once. One (PID 16392, PPID=1 — orphaned) was a leftover from an earlier, interrupted invocation whose own run_matrix.py parent had already died without the subprocess dying with it; the other was the current, legitimate run attached to the live terminal. Killed only the orphan (verified by PPID before touching anything) — physical memory was sitting at 15G/~15G used with 132M unused at the time, so the duplicate alone plausibly explains the slowdown. Fixed at the root: run_matrix.py now refuses to launch any session that's already running, checked live via pgrep rather than a lockfile that could itself go stale across a crash — caught and fixed a bug in the guard itself before trusting it, too: macOS's pgrep is BSD regex, not GNU/PCRE, and silently matches nothing with \s (verified directly), so the boundary now uses [[:space:]] — needed for real, since several session names here are literal prefixes of others (e.g. kfm12_sync_m480_20ep vs. …_seed1) and a bare substring match would have false-positived across them.
